# Архитектурное решение по трейсингу

## 1. Вводные

Необходимо внедрить инструмент, с помощью которого команда сможет увидеть, что происходило с заказом и где он находится сейчас.

## 2. Анализ внедрения трейсинга

Критические точки, где заказ может зависнуть или потеряться:

| Компонент<br />системы                       | Риски                                                                                                                                                            | Почему трейсинг обязателен                                                                                                                                                                          |
| ------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Shop API**                                           | • Не отправлено сообщение в RabbitMQ<br />после создания заказа.<br />• Ошибка загрузки 3D-файла в S3. | Начальная точка жизненного цикла заказа.<br />Без трейсинга невозможно определить, дошёл ли заказ до очереди.                       |
| **RabbitMQ**                                           | • Потеря сообщений из-за DLQ.<br />• Задержки обработки (очередь растёт).                                          | Сообщения — основной способ коммуникации между CRM и MES.<br />Трейсинг покажет путь сообщения и точку потери.                            |
| **CRM API**                                            | • Не обработано событие из очереди (например,`OrderCreated`).<br />• Ошибка синхронизации со Shop DB.    | CRM управляет статусами заказов.<br />Отсутствие трейса скроет ошибки в бизнес-логике <br />(например, не подтверждён платёж). |
| **MES API**                                            | • Не назначены операторы.<br />• Некорректный расчёт цены <br />из-за ошибки в 3D-модели.                | MES отвечает за производство.<br />Если заказ «завис» здесь, клиент не получит уведомление о задержке.                                        |
| **Синхронизация <br />Shop DB ↔ MES DB** | • Расхождение статусов<br />(например, в CRM заказ «в работе», <br />в MES — «отменён»).                        | Трейсинг покажет, какой сервис изменил статус последним и почему.                                                                                                    |

### Список систем, которые необходимо покрыть трейсингом

1. **Shop API** (Spring Boot)
2. **CRM API** (Spring Boot)
3. **MES API** (C#)
4. **RabbitMQ** (через интеграцию с заголовками сообщений)

Не включаем:

- Фронтенды (Shop Frontend, CRM Frontend, MES Frontend) — трейсинг начнётся с API.
- Базы данных и S3 — их метрики уже отслеживаются через USE, но ошибки операций должны логироваться в рамках спанов сервисов.

### **Данные, которые должны попадать в трейсинг**

| Категория                        | Данные                                                                                                                                                                                       | Зачем нужны                                                                                                                                                     |
| ----------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Идентификаторы**    | •`order_id` (бизнес-идентификатор заказа)<br />• `trace_id`, `span_id` (технические)                                                                   | Связь всех этапов обработки заказа в распределённой системе.                                                          |
| **Статусы и этапы**    | • Текущий статус («создан», «ожидает оплаты», «в производстве»)<br />• Источник изменения статуса (CRM API / MES API) | Выявление «зависаний»:<br />например, заказ 2 часа в статусе «ожидает назначения оператора».     |
| **Тайминги**                | • Время входа / выхода из каждого сервиса<br />• Длительность операций (валидация 3D-модели, расчёт цены)           | Обнаружение узких мест:<br />например, MES API обрабатывает заказ 10 минут <br />из-за ошибки в C#-коде. |
| **Контекст ошибок**   | • Тип исключения (например,`S3UploadFailed`)<br />• Стек-трейс и параметры запроса                                                              | Ускорение отладки:<br />сразу видно, почему заказ не дошёл до оператора.                                           |
| **Данные о 3D-модели** | • Путь к файлу в S3<br />• Результаты валидации (объём, толщина стенок)                                                                          | Если заказ отклонён в MES, можно проверить,<br />была ли проблема в файле.                                            |
| **Интеграции**            | • Имя очереди RabbitMQ (например,`order.created`)<br />• ID сообщения в очереди                                                                             | Отслеживание пути сообщения:<br />например, сообщение застряло в DLQ из-за невалидного JSON.            |
| **Операторы**              | •`operator_id`, назначенного на заказ <br />• Время взятия заказа в работу                                                                          | Анализ нагрузки на операторов и балансировка.                                                                                      |

## 3. Мотивация

Внедрение трейсинга решит критическую проблему **потери** и **зависания заказов** в распределённой системе, где интеграция через RabbitMQ и разрозненные БД (Shop DB, MES DB) создаёт «слепые зоны». Без сквозного контекста команды тратят часы на ручную диагностику, а бизнес теряет деньги из-за срывов SLA и отменённых заказов.

### **Бизнес-метрики**

* Среднее время выполнения заказа : сокращение с 48 до 36 часов (−25%) за счёт устранения зависаний между CRM и MES.
* Количество отменённых заказов : снижение с 7% до 2% из-за потери сообщений на этапе передачи в MES.
* NPS клиентов : рост на 15 п.п. за счёт прозрачности статусов (сейчас 15% жалоб — «оплачено, но нет подтверждения»).

*Примечание: цифры взяты примерные, будем считать это целевым KPI внедрения трейсинга*

### **Технические метрики**

* MTTR : сокращение с 4 часов до 20 минут при инцидентах, связанных с заказами.
* Доля потерянных сообщений в RabbitMQ : снижение с 0.3% до 0.05% за счёт детектирования DLQ-сценариев через трейсы.

Эти метрики напрямую влияют на выручку и операционную эффективность. Сокращение времени обработки заказа ускорит оборачиваемость, а снижение отмен — сохранит 5–7% выручки в пиковые периоды. Технические улучшения снизят нагрузку на команды поддержки на 40%, высвободив ресурсы для развития системы вместо тушения пожаров. Трейсинг станет основой для автоматизации реакции на сбои (например, авто-реинжекция сообщений из DLQ), что сделает систему устойчивой к сезонным нагрузкам.
