# Выбор и настройка мониторинга в системе

## 1. Описание текущей архитектуры

- Архитектура:
  - интернет‑магазин (Vue + Spring Boot)
  - CRM (Vue + Spring Boot)
  - MES (React + C#)
  - шина RabbitMQ
  - 3D‑файлы в S3
  - по одному инстансу каждого приложения и БД
  - окружения dev / release / prod.
  - метрики сайта через Яндекс.Метрику покрывают только фронт
  - партнёрские интгерации по API не покрыты !!!
- Проблемы:
  - "пропавшие" / зависшие заказы
  - заказы не в срок
  - жалобы партнёров по API
  - медленная первая страница MES.
- Ограничения:
  - рост нагрузки (ежемесячно +100 заказов)
  - длительный расчёт стоимости в MES (средне 2–3 мин, до 30 мин на сложных моделях)
  - интеграция CRM - MES по RabbitMQ.

## 2. Мотивация внедрения мониторинга

Без наблюдаемости невозможно:

- заранее узнавать о потенциальных проблемах, бизнес продолжит получать обратную связь и информацию об ошибках через негатив от клиентов и партнёров
- проанализировать прямой путь обраьотки заказа и найти в какой системе "бутылочное горло"
- объяснить бизнесу истинные причины нарушения SLA и потерь заказов
- подтвердить эффект от внедряемых изменений (кеши, CQRS, DLQ, outbox и т. д.)
- предупредить инциденты, на основе метрик понять что каких-то ресурсов скоро начнёт не хватать и нужно масштабироваться или потимизировать архитектуру.

Ожидаемый эффект:

- сокращение времени расследования инцидентов
- умееньшение процента "потерянных/зависших" заказов
- ускорение главной страницы MES
- видиомость в моменте, какая система начинает сбоить и требует внимания (увеличение времени ответа, ошибок)
- получение статистики о работе системы, составление обоснованных требований SLA

## 3. Подход к мониторингу

Будем использовать разные подходы:

- **4 золотых сигнала** — для всех HTTP‑API.
  - shop_api, crm_api, mes_api
- **RED** — для внешних интеграций и внутренних API.
  - shop_api, crm_api, mes_api
- **USE** — для инфраструктуры: CPU / Memory / Disk / Network - приложений, БД, брокера сообщений, хранилища.
  - s3_storage, shop_db, mes_db, rabbitmq

## 4. Какие метрики, где и для чего будем использовать

### 1. HTTP-API (shop_api, crm_api, mes_api)

**Что отслеживаем** :

- RPS (метрики 3,4,5) - База для RED-метода

  - Number of requests (RPS) for internet shop API
  - Number of requests (RPS) for CRM API
  - Number of requests (RPS) for MES API
- HTTP 500 (28,29,30) - База для RED-метода

  - Number of HTTP 500 for shop API
  - Number of HTTP 500 for CRM API
  - Number of HTTP 500 for MES API
- Latency (19,20,21) - База для RED-метода

  - Response time (latency) for shop API
  - Response time (latency) for CRM API
  - Response time (latency) for MES API
- Сессии (32,33,34) — показатель Saturation из 4 золотых сигналов.

  - Number of simultanious sessions for shop API
  - Number of simultanious sessions for CRM API
  - Number of simultanious sessions for MES API

**Зачем** :

- RPS и latency помогают выявить аномалии (например, всплеск трафика перед падением).
- HTTP 500 без детализации по endpoint бесполезны — нужны ярлыки.

**Ярлыки**:

- `endpoint` — чтобы понять, какой метод ломается (например, `/upload-3d-model`).
- `client_type` — отличить мобильное приложение от интеграции с MES.

**Что добавить ещё** :

- HTTP 4xx ошибки (например, 429 Too Many Requests) — критично для защиты от атак.
- P95/P99 latency — среднее latency скрывает "хвосты" медленных запросов.
- Number of requests (RPS) for internet shop API
- Number of requests (RPS) for internet shop API
- Number of requests (RPS) for internet shop API
- Number of requests (RPS) for internet shop API

### 2. Базы данных (shop_db, mes_db)

**Что отслеживаем**:

- Memory (15,16) — минимальный набор USE
  - Memory Utilisation for shop db instance
  - Memory Utilisation for MES db instance
- Connections (17,18) — минимальный набор USE.
  - Number of connections for shop db instance
  - Number of connections for MES db instance

**Зачем**:

- Утечки памяти или исчерпание соединений — частые причины падений.

**Ярлыки**:

- `query_type` — выявить "тяжелые" SELECT/INSERT.

**Что добавить ещё** :

- Нет **CPU utilization для БД** — невозможно оценить нагрузку на CPU-bound запросы.
- Нет **disk latency** — критично для медленных HDD/S3-хранилищ.
- Нет **disk usage** — критично для производительности и стабильности работы файловой системы

### 3. RabbitMQ

**Что отслеживаем**:

- DLQ (метрика 1)
  - Number of `dead-letter-exchange` letters in RabbitMQ
- In flight (метрика 2)
  - Number of message `in flight` in RabbitMQ

**Зачем**:

- DLQ растет — значит, события (например, `OrderCreated`) не обрабатываются.
- `in flight` > 1000 — признак перегрузки потребителей.

**Ярлыки**:

- `queue_name` — разделить очереди для CRM/MES.

**Что добавить**:

- Queue length — рост длины очереди = проблемы с обработкой.
- CPU/Memory RabbitMQ — нет в списке, но критично для кластера, например, для RabbitMQ лучше иметь запас по памяти более чем `x2` из-за особеннойстей работы (копирование вставкой и т.д.)

### 4. S3 Storage

**Что отслеживаем**:

- Размер (метрика 22)
  - Size of S3 storage.

**Зачем**:

- Рост размера без контроля — риск превышения лимитов и cost-взрыв.

**Что добавить**:

- Request error rate — ошибки при загрузке 3D-моделей критичны для бизнеса.
- Latency — медленная загрузка файлов убивает UX в 3D-редакторе.

---

### Что ещё, чего нет в списке, хорошо бы добавить

1. HTTP 4xx ошибки для всех API — без этого невозможно отследить атаки или баги в клиентских приложениях.
2. CPU utilization для БД и RabbitMQ — в текущем списке есть CPU только для API, что недостаточно.
3. Latency для S3 — задержки при работе с 3D-файлами напрямую влияют на пользовательский опыт.
4. Slow queries count в БД — медленные запросы — главная причина деградации производительности.

---

### Как это будет работать на практике

**Алертинг**:

- Если **DLQ в RabbitMQ > 0** — срочное уведомление команде интеграций.
- Если **P99 latency shop_api > 2s** — проверка нагрузки на 3D-редактор.

**Оптимизация**:

- **Рост размера S3 + падение скорости загрузки** — сигнал к архивации старых моделей.
- **Высокий % HTTP 500 в MES API** — фокус на валидацию данных из CRM.

**Планирование capacity**:

- **Рост числа соединений к shop_db** — основание для горизонтального масштабирования.

Такой подход закроет 80% рисков, связанных с отказами и деградацией сервисов, при минимальных затратах на инфраструктуру мониторинга.

## 5. План действий (драфт ТЗ)

1. **Развернуть Prometheus + Grafana** (managed или self‑hosted) с HA‑storage.
2. **Подключить экспортеры**:
   - node_exporter на всех инстансах;
   - postgres_exporter для shop_db и mes_db;
   - rabbitmq_exporter на брокере;
   - включить `/actuator/prometheus` в Spring Boot (Shop/CRM);
   - включить `prometheus-net` middleware в MES API.
3. **Единая схема лейблов** и базовые дашборды 4 Золотых Сигнала/USE/RED.
4. **HTTP‑метрики по эндпоинтам**: latency histogram с `le`‑buckets: `50, 100, 200, 300, 500, 1000, 2000, 5000 ms`.
5. **Очереди**: включить DLX/DLQ; алерты на DLQ прирост и возраст сообщений.
6. **БД**: алерты на `connections_used > 80%`, "долгие транзакции", рост размера.
7. **S3**: сбор размера бакета и ошибок операций (экспортер/облачные метрики).
8. **SLO и алерт‑политика**: договориться с бизнесом об error‑budget и приоритизации работ.
9. **Дашборды по ролям**

- "Бизнес KPI заказа"
- "Операторы MES"
- "API партнёров"
- "Инциденты"

10. **Документация и обучение**: составление runbooks, ссылки на дашборды и алерты, on‑call расписание.

**Ключевые KPI для оценки успеха**:

- Сокращение MTTR (Mean Time To Resolve) на 30% за 3 месяца за счёт раннего выявления проблем через алерты.
- Покрытие метриками 100% критичных компонентов (API, БД, RabbitMQ, S3).
- Снижение числа инцидентов из-за перегрузки ресурсов (CPU/memory) на 50% через алерты по USE-метрикам.

**Риски и митигация**:

- Риск: Перегрузка при высокой детализации метрик.
  Решение: Настроить downsampling (уменьшение детализации) и ограничить retention для не критичных метрик.
- Риск: Ложные срабатывания алертов.
  Решение: Итеративно настраивать пороги на основе исторических данных (2–3 недели «тихого» сбора).

## 6. Показатели насыщенности

- DB connections > 80% от max_connections — рост ошибок подключения и очередей -> пулы, лимиты, оптимизация запросов, поднятие read-реплик.
- RabbitMQ: более 1000 сообщений в очереди -> алерт сотрудникам, возможно поднятие дополнительных инстансов потребителей.
- HTTP: error‑rate 5xx > 1% (5m) или p95 latency выше SLO — деградация сервиса/зависимости -> алертинг сотрудникам, анализ причин, если было обновление - rollback публикации.
- Прописать стратегию ужесточения ratelimit - лучше обслужить часть клиентов, чем положить всю систему.
